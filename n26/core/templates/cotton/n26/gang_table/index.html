A grid keeps both: one column on a phone with the row's parts stacked, and at md the same rows snap into columns that line up down the page. Rows register their facets on init and show themselves only while those pass, so the count and the list are computed from one object and cannot disagree. --- two searches, one box --- The box narrows what is on the page as you type; clicking Search asks the server, which can reach gangs this page never carried. Given an `action` it does both: typing is the fast answer to a question the page can already answer, submitting is for when it cannot. `query` is what the server was asked, and the box opens holding it. That is also what keeps the two out of each other's way: while the box still reads what the server answered, the in-page filter passes every row, because the rows on the page *are* the answer — narrowing by that query again would hide any row the server matched by means a substring does not have (a word stem, a field the row does not print). Type something else and it narrows from there as usual. :type_options — [{value, label}] of every gang type present. Drawn only when there are two or more: a filter with one option filters nothing. noun — what the count counts, and its singular for a count of one. Pass it as an expression: through an attribute it is escaped twice and a quote in the query comes back as `&quot;`. empty — what to show when a search matches nothing. total — how many the whole answer holds, where the rows are one page of it.
